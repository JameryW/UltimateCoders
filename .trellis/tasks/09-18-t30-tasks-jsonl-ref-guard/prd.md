# T30 / #680 —— 给 `.trellis/tasks` 的 jsonl 引用建守卫（#678 选项 C 的落地）

**Issue**: #680（P3）  **Parent**: 无  **Branch**: `main`

## 问题

`.trellis/tasks/**` 下被 git 跟踪的 `*.jsonl` 用 `{"file": ".trellis/..."}` 记录任务上下文。
这些引用**不在任何守卫的索引里**：

- `scripts/check-spec-refs.py` 的语料是 `SPEC_DIR = .trellis/spec`（实测：全文 `jsonl` /
  `.trellis/tasks` **零命中**）⇒ 任务上下文引用**无覆盖**。

⇒ 归档移动目录后，引用静默悬空且无人报。这正是 **#678** 的诊断；该票的 **A**（归档时重写自引用）
已由 `7ba7ad8` 交付、存量由 `f3ee6dd` 迁移，但**它自己写的建议是「A + C」而 C 从未落地**。

## 一手测量（2026-09-18）

| 量 | 值 |
|---|---|
| JSON 载体里 `file` 键的 `.trellis` 引用 | **787**（含本票自己的载体时为 **787**；见下）|
| **悬空** | **14**（#678 关闭评论记录 **7** ⇒ 漏 7）|
| **MALFORMED**（行不是合法 JSON） | **47**（**本票范围外**，见下）|

14 条的形状（详见 #680）：**9 条目标是被移动的产物**（其中 2 条是**新形状**：产物住在
`JameryW/workspace`、归档时目录套目录）、**3 条目标是已删除的 spec**、**2 条目录写错**。

### 787 的口径澄清（实测，非推理）

先前我曾写「788，因为本票自己的 jsonl 被计入」。**这是错的**，已实测更正：
把 `.trellis/tasks/09-18-t30-tasks-jsonl-ref-guard/` **临时移出仓外**再跑守卫，
数字**不变**（`773 ok / 14 dangling / 47 malformed`）。

原因：本票的 `implement.jsonl` 里确实有 9 处 `.trellis` 字面量，但**全部出现在
`detail` 散文里**（如 `.trellis/tasks/` `` `.trellis/workspace/JameryW/tasks/`），
而守卫**只统计 `file` 键**。⇒ 本票载体对基线贡献 **0**。
**教训**：数「引用」必须用**守卫自己的口径**；我用 `grep` 数全部 `.trellis` token
得到 9，那是在数另一个量。

### 47 条 MALFORMED —— 独立缺陷类，**本票不做**

守卫首次真跑就报出 47 行「不是合法 JSON」，分布在 5 个 2026-06/09 的归档任务：

| 载体 | 行数 |
|---|---|
| `06-24-multi-repo-config/implement.jsonl` | 13 |
| `06-24-multi-repo-config/check.jsonl` | 7 |
| `09-14-t9-merge-barrier/implement.jsonl` | 8 |
| `09-15-t12-affinity-placement/implement.jsonl` | 8 |
| `09-14-t10-context-compiler/implement.jsonl` | 7 |
| `09-14-t11-env-allowlist/implement.jsonl` | 4 |

**根因（实测）**：这些文件是**把 JSON 数组写进了 `.jsonl`**，不是文件损坏。
每个物理行以 `,` 结尾（数组元素分隔符），末行是 `}` 而**没有**闭合 `]`。

**可恢复性（实测）**：**去掉行尾逗号后逐行 `json.loads` 全部通过**
（9/9、8/8、8/8、4/4；`06-24` 两个文件整文件 `json.loads` 直接得到 `list`）。
⇒ **无数据丢失**，是格式约定错用。

**关键判据 —— 这 47 行是否藏有悬空引用？实测：没有。**
把 6 个文件全部按上述方式恢复后取 `.trellis` 引用（`file` 与 `path` 两种键），
共 **2 条，全部可解析，悬空 0**。
⇒ 本票的 **14 条不是漏计**，两个缺陷类**互相独立**。

**范围外，理由**：本票要治的是「引用必须可解析」；而这 47 行的缺陷是
「载体不是合法 JSONL」，**修法、判据、风险都不同**（动的是归档记录的内容格式）。
按仓规「本 issue 只记录测量与根因，不臆造」⇒ 在此**记账**，另裁。

## 本票范围（**只做 C**）

**要**：把「`.trellis/tasks/**/*.jsonl` 的 `.trellis` 引用必须可解析」做成检查器 —— **治复发**。

**不要**：
- ❌ **不做存量重指（#678 的 B 类）**：动的是已完成任务的归档记录；且 14 条里 2 条是**新形状**
  （退役身份目录 / 嵌套重复目录），判定规则不唯一 ⇒ **机械回填会写错**。B 单独裁。
- ❌ 不改 `check-spec-refs.py` 的语料边界（它是 spec 面的守卫，各自独立）。
- ❌ 不碰产品代码。

## 验收

1. 新检查器 `scripts/check-tasks-refs.py` 存在，`--audit` 可列出逐条悬空。
2. 索引源 = **`git ls-files` ∩ `EXCLUDE_DIRS`**（T26 教训：`os.walk` 会看见被 gitignore 的文件
   ⇒ 同一提交两个判词）。
3. **exit code 语义明确**：本票裁决见下（结构性失败才非零）。
4. 有**测试级**覆盖 + **消融自检**：一次一处突变、确认变红、按字节恢复、由**独立进程**复算 sha256。
5. CI 走**独立小 job**、**明确不设 `paths`**（该守卫读全仓开放集，过滤会蒙住它 —— T26/T29 判据）。
6. 守卫对**真实语料**跑出的数字必须能被独立复算（本票：**787 refs / 14 dangling /
   47 malformed**；后两项与 #680 记录一致）。
7. **`MALFORMED` 是结构性失败（exit 非零）**，且**本票不修那 47 行** ——
   它的存在必须由第 6 条的基线数字**显式承载**，不得为了「让守卫变绿」而把它降级成 advisory
   或加白名单。测试须覆盖：注入一行坏 JSON ⇒ 报 MALFORMED 且非零。

## 已知设计点

1. 索引必须走 `git ls-files`（理由同上）。
2. **不加 `paths` 过滤**。
3. 沿用 `git ls-files` **∩** `EXCLUDE_DIRS` 的形状（`.scratch/` 被 gitignore，但历史上曾有被跟踪的
   `.scratch/**` 文件，见 `check-spec-refs.py` 的注释）。

## 裁决（本票当场定，写明理由）

- **exit code**：**结构性悬空 = 非零**（与 journal 账本守卫同类：这是一份**可预期的有限清单**，
  且可由 `archive_task_dir` 的自愈路径不再产生新的 ⇒ 红是可修的）。
  ⚠️ **不设 `EXPECTED_DANGLING` 白名单**：那是「把红关掉」而不是修它；14 条已在 #680 记账。
- **basename-only 命中**（2 条 `type-safety.md` 目录写错）：计为**悬空**（路径写法错误，与
  `check-spec-refs.py` 的 `PATH_FORM` 同类），不是 advisory。

## 实现期实测（写下来，因为都推翻/收紧了本票自己的初稿）

1. **`--root` 是必需的，不是便利**。首版守卫的 `ROOT` 由 `__file__` 推导 ⇒ 合成仓测试其实在审**真仓**；
   第一批测试全绿是**巧合**（数字碰对了）。⇒ 加 `--root DIR`（测试用；CI 裸跑，保证判词只关于该提交）。
2. **语料必须也是跟踪集**。首版**索引来自 git、语料来自文件系统 `rglob`** ⇒ 未跟踪的 `.jsonl` 会被审
   ⇒ **同一提交两个判词**（T26 缺陷从索引搬到语料）。⇒ 语料改为跟踪集，并由
   `test_untracked_carrier_is_not_audited` 钉住。**实测**：语料改跟踪集前后，工作树与干净检出
   的数字从「788/787 不一致」变成**两侧同为 787 / 14 / 47**。
3. **基线数字的口径**（更正初稿）：本票 `implement.jsonl` 只有 **1** 条 `file` 引用
   （`.trellis/workflow.md`）。因为它**未提交**，守卫读到 **787**；`git add` 之后读到 **788**。
   两者都合法，测试断言 `in (787, 788)`。
4. **CRLF 轴没法被钉住 —— 因此删掉了那个测试**（诚实记账，不是「已覆盖」）：
   本仓 `core.autocrlf=true` ⇒ 同一提交在本机是 CRLF、在 CI 是 LF。**实测**：真实语料 **542/577**
   个载体是 CRLF、**0** 个含孤立 CR；守卫用 `splitlines()` + `line.strip()` ⇒ **天生 EOL 无关**。
   两次突变尝试都失败：① 改尾随 CR 分支 ⇒ 只是让守卫**崩溃**（崩溃会打红测试但不钉住任何东西）；
   ② `split("\n")` 取代 `splitlines()` ⇒ **零效果**（`strip()` 已去掉 CR）。
   ⇒ 删掉 `test_crlf_working_tree_gives_the_same_verdict` 与对应突变。
   **判据**：一个永远不会红的测试是装饰，不是覆盖；留着一个假突变会让「6 个突变全红」变成假话。
5. **47 条 MALFORMED 的一次手查**：`09-14-t9` 等 4 个文件去掉行尾逗号后**逐行 `json.loads` 全通过**；
   `06-24` 两个文件整文件是合法 JSON `list`。⇒ **无数据损坏**，是「把 JSON 数组写进 `.jsonl`」。
   恢复后取 `.trellis` 引用（`file` 与 `path` 两键）共 **2 条、悬空 0** ⇒ 本票的 **14 不是漏计**。
6. **自检脚本的鲁棒性**：机器高负载下 pytest 可能**未启动**，此时每个红集都是空集 ⇒ 会被误读成
   「所有突变无效」（曾观测到 1 次，报 21 个问题）。⇒ `run_tests()` 现在「没跑到 summary 就抛错」。
   sha256 认证也加了**一次重试**（空读是瞬时现象，但不能静默接受）。

- **MALFORMED 的处置**：**报出来且非零**，但**不在本票修**。理由：一个「静默跳过的不可解析行」
  正是这类缺陷的藏身处（若吞掉，`06-24` 那 20 行引用就永远无人看）；而修它属于另一个缺陷类。
  ⇒ 本票提供**测量**与**守卫**，**不含**存量修复。**不为这 47 行加白名单**（同 DANGLING 的理由：
  白名单是把红关掉，不是修它）。
